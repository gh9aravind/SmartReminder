# Smart Reminder — Cross-Platform Task Reminder App

React Native (TypeScript) + Supabase (Auth, Postgres, RLS, Realtime) + local SQLite
offline-first storage + local push notifications.

## 1. Architecture Overview

```
UI (Screens)
   │
   ▼
Zustand Store (src/store)          ← single source of truth for the UI
   │
   ▼
Task Service (src/services)        ← business logic: always writes to SQLite first
   │                │
   ▼                ▼
Local SQLite      Sync Manager (src/sync)
(src/db)             │
                      ▼
                Supabase Postgres (RLS-protected)
                      │
                      ▼
              Realtime channel → pushes remote changes back into SQLite
```

**Why offline-first?** The UI never talks to Supabase directly. Every read comes from
SQLite, and every write goes to SQLite first and is marked `pending`. The `syncManager`
then pushes pending rows to Postgres whenever a connection is available (on app start,
on reconnect, and after every local write), and pulls remote changes down via Realtime.
This means the app is fully usable offline, and nothing is ever lost — a create/edit made
mid-flight is just replayed once connectivity returns.

**Why RLS instead of app-level checks?** Row Level Security enforces `auth.uid() = user_id`
directly in Postgres, so even if a client were compromised or a request bypassed the app
entirely, a user physically cannot read or write another user's rows — the database
guarantees it, not the client code.

```
smart-reminder-app/
├── .github/workflows/build.yml   # CI/CD: lint, test, build APK
├── supabase/schema.sql           # Tables, RLS policies, triggers, realtime
├── src/
│   ├── config/supabaseClient.ts  # Supabase client init
│   ├── db/                       # Local SQLite (schema + repository)
│   ├── services/                 # authService, taskService (offline-first CRUD)
│   ├── sync/syncManager.ts       # Push/pull reconciliation logic
│   ├── notifications/            # Local reminder scheduling (Notifee)
│   ├── store/taskStore.ts        # Zustand state for the UI
│   ├── navigation/                # React Navigation stack
│   ├── screens/                  # Login, TaskList, TaskForm
│   ├── types/                    # Shared TS types
│   └── App.tsx                   # Root: DB init, auth listener, sync wiring
├── __tests__/                    # Jest unit tests
├── .env.example
└── package.json
```

> Native `android/` and `ios/` folders aren't included here — they're generated by the
> React Native CLI in step 2 of the roadmap below, then this `src/` folder and config
> files are dropped in on top.

## 3. Step-by-Step Roadmap

1. **Create the Supabase project**
   - Create a project at supabase.com.
   - Open the SQL Editor and run `supabase/schema.sql` from this repo.
   - Enable Email auth under Authentication → Providers. For Google, add your OAuth
     Client ID under Authentication → Providers → Google.
   - Copy your Project URL and anon public key (Settings → API) into `.env`
     (based on `.env.example`).

2. **Scaffold the native project**
   ```bash
   npx react-native init SmartReminder --template react-native-template-typescript
   ```
   Then copy this repo's `src/`, `index.js`, `app.json`, config files, and
   `.github/` folder into the generated project (overwrite the defaults).

3. **Install dependencies**
   ```bash
   npm install
   cd ios && pod install && cd ..   # macOS only, for iOS
   ```

4. **Google Sign-In setup** (for `signInWithGoogleIdToken` in `authService.ts`)
   - Install and configure `@react-native-google-signin/google-signin` per its docs
     (Android SHA-1 fingerprint + `google-services.json`, iOS `GoogleService-Info.plist`).
   - In `LoginScreen.tsx`, call `GoogleSignin.signIn()` to get an `idToken`, then pass
     it to `signInWithGoogleIdToken(idToken)`.

5. **Run locally**
   ```bash
   npm run android   # or: npm run ios
   ```
   Sign up a test user, create a task with a near-future due date, and confirm a local
   notification fires. Turn on airplane mode, create/edit a few tasks, then reconnect —
   watch `sync_status` flip from `pending` to `synced`.

6. **Set up CI/CD secrets** (Repo → Settings → Secrets and variables → Actions)
   - `SUPABASE_URL`, `SUPABASE_ANON_KEY` — required.
   - `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_PASSWORD` —
     optional; only needed for a signed release build. Without them, Gradle falls back
     to the auto-generated debug keystore.

7. **Push to `main`**
   - Every push/PR runs lint + typecheck + unit tests.
   - Pushes to `main` additionally build the Android APK and upload it as a workflow
     artifact (Actions tab → the run → Artifacts → `app-release-apk`).

8. **Harden for production**
   - Add pagination/virtualized lists once task counts grow.
   - Add a conflict-resolution strategy beyond last-write-wins if multi-device editing
     is a priority (e.g. version column + merge UI).
   - Add Sentry/Crashlytics for crash reporting.
   - Add an iOS build job (macOS runner + `xcodebuild`) alongside the Android one.

## 4. Key Design Decisions

| Decision | Reasoning |
|---|---|
| `client_id` column on `tasks` | Lets an offline-created row (with a local UUID) map cleanly to its eventual Postgres row without ID collisions. |
| Soft delete (`is_deleted`) | A hard `DELETE` can't be synced to a client that was offline when it happened — the client needs a deletion *event* to pull, not just an absent row. |
| `sync_status` column locally | Makes the sync queue explicit and inspectable, instead of guessing what changed by diffing. |
| Realtime subscription | Keeps multiple devices/sessions for the same user converged without polling. |
| RLS on every table | Database-enforced tenant isolation; the app code becomes a second layer of defense, not the only one. |
